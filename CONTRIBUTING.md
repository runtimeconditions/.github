# Contributing

Thanks for contributing to Runtime Conditions! These guidelines apply across
the organization unless a repository provides its own contribution guidelines.

## Start with an issue

Every pull request must be linked to an issue.

Before starting work, check for an existing issue describing the bug, feature,
or improvement. If none exists, open one explaining:

- The problem you want to solve.
- Your proposed approach.
- Any alternatives or compatibility concerns.

For major features or substantial changes, discuss the approach with the
maintainers before beginning implementation so we can agree on scope.

## Developing your contribution

- Follow the repository's setup instructions and coding conventions.
- Keep changes focused on the linked issue.
- Add or update tests when the change affects behavior.
- Run the applicable tests, formatting checks, and other validation described
  in the repository.
- Include applicable documentation and update existing documentation affected
  by your changes.

## Submit complete work

Each pull request must be feature complete within its agreed scope. It must
include the implementation, applicable tests, and documentation needed to
deliver the proposed change.

Do not submit incremental, unfinished work, placeholder implementations, or
changes that depend on future pull requests to become usable.

If a major feature requires extended development, discuss it with the
maintainers. We can establish a long-running feature branch for you to develop
against and agree on how the work will be reviewed and integrated.

## Opening a pull request

Use a clear title and describe:

- What changed and why.
- The issue this pull request addresses, including a link.
- How you tested the change.
- Any breaking changes or migration steps.

Before submitting, confirm that:

- [ ] The pull request is linked to an issue.
- [ ] The work is feature complete within the agreed scope.
- [ ] Applicable tests have been added or updated.
- [ ] Applicable checks pass.
- [ ] Relevant documentation has been added or updated.

## Attributed authors

We will only accept commits that are attributed as authored by real humans.
The reason for this is that we can only accept code from those who can be 
responsible and accountable for their work. While it may be tempting, or
default behavior in some environments, to credit a coding agent as a co-
author, an agent has no capacity for accountability, and therefore cannot be
accepted as a commit author.

## Review process

Maintainers may request changes before merging. Respond to feedback and keep
the pull request description current as the implementation changes.

If the scope needs to change substantially, discuss it in the linked issue
before expanding the pull request.
